# unformat

把 `format()` 写出去的字符串，用**同一段格式描述**读回成 Python 值。

单文件、只用标准库、零配置。Python 3.10+ 直接跑，不需要安装任何依赖。

```bash
python unformat.py "{c:02d}" "100"
# c = 100
```

`"100"` 在这里能被读回来，是因为 `"{c:02d}".format(c=100)` 写出来的正是 `"100"`。
宽度 2 是**下限**而不是截断长度——这是很多按正则猜字段长度的解析器容易读错的地方。

---

## 为什么值得单独做一个

Python 的 `format()` 能把值变成文本，但标准库没有反过来的一步。常见的做法是
给每种类型手写一套正则：`d` 匹配数字、`x` 匹配十六进制、`f` 匹配浮点……
然后还要各自处理宽度、对齐、填充符、千分位、精度、日期指令。

问题是这套正则和 `format()` 是两套独立实现，迟早会分叉：

```pycon
>>> "{c:02d}".format(c=100)
'100'
>>> "{x:03x}{y:03x}".format(x=1, y=2)
'001002'
>>> "{:,.1%}".format(12.345)
'1,234.5%'
>>> "{name:.>16.16}".format(name="Joe")
'.............Joe'
```

上面四行都是合法的 `format()` 输出，但靠正则猜长度的解析器，往往读不回第一、
第二、第三行，或者把第四行的填充点号当成值的一部分。

`unformat` 不猜。它只认一条规则：

> **读到的值，重新交给 `format()` 用同一段 spec 写回去，必须能复原捕获到的原文。**

于是宽度、对齐、填充、千分位、精度、日期全部由 `format()` 自己定义，
不需要为每种类型维护一套正则，也不存在「写得出来却读不回来」的分叉。
匹配失败时给一张逐字段的判定表，而不是一个安静的 `None`。

## 直接用

下载 `unformat.py` 放到项目里就能用，也可以整仓 clone。

```bash
# 命令行
python unformat.py "It's {}, I love it!" "It's spam, I love it!"
# [0] = 'spam'

python unformat.py "{name:.>16.16}" ".............Joe"
# name = 'Joe'

python unformat.py "{x:03x}{y:03x}" "001002"
# x = 1
# y = 2

# 作为模块
python -c "from unformat import parse; print(parse('Age: {age:d}', 'Age: 42')['age'])"
# 42
```

### Python API

```python
from unformat import parse, compile, search, findall

r = parse("It's {}, I love it!", "It's spam, I love it!")
r[0]                       # 'spam'
r.fixed                    # ('spam',)

r = parse("{x:03x}{y:03x}", "001002")
r["x"], r["y"]             # (1, 2)
r.named                    # {'x': 1, 'y': 2}
r.spans                    # {'x': (0, 3), 'y': (3, 6)}
r.as_dict()                # 可直接 json.dumps

parse("Age: {age:d}", "Age: nope")   # None，不抛异常

# 批量处理时编译一次就够
p = compile("id={id:d} level={level}")
for line in open("app.log", encoding="utf-8"):
    hit = p.parse(line.rstrip("\n"))
    if hit:
        print(hit["id"], hit["level"])

search("[{n:d}]", "noise [7] noise")["n"]                    # 7
[h["n"] for h in findall("[{n:d}]", "[1] [22] [333]")]      # [1, 22, 333]
```

## 命令行

```
python unformat.py FORMAT [TEXT] [选项]
```

| 选项 | 作用 |
|------|------|
| `--explain` | 打印逐字段候选判定表，说明为什么匹配 / 为什么没匹配 |
| `--json` | 输出 JSON，方便管道和脚本消费 |
| `--search` | 在文本里搜索，而不是要求整串匹配 |
| `--all` | 找出全部匹配（配合 `--search`） |
| `--ignore-case` | 字面量忽略大小写 |
| `--version` | 打印版本 |

`TEXT` 省略时从标准输入逐行读取，格式串只编译一次：

```bash
$ printf 'id=1 level=INFO\nid=2 level=WARN\n' | python unformat.py "id={id:d} level={level}" --json
{"ok": true, "fixed": [], "named": {"id": 1, "level": "INFO"}, "spans": {"id": [3, 4], "level": [11, 15]}, "text": "id=1 level=INFO"}
{"ok": true, "fixed": [], "named": {"id": 2, "level": "WARN"}, "spans": {"id": [3, 4], "level": [11, 15]}, "text": "id=2 level=WARN"}
```

匹配失败时退出码是 1，格式串本身写错时是 2，方便在脚本里判断。

### 读不出来时，看它为什么读不出来

```bash
$ python unformat.py "{:d}" "abc" --explain
格式串 : {:d}
输入   : 'abc'

逐段候选判定（能逐字节写回的切分点会优先采用）
------------------------------------------------------------------------------
  [ 0] 字段 {:d}           @  0:0   取 ''
       去掉填充 '' -> 值 None -> 写回 ''  不通过（仅去填充后一致）
       原因：{:d} 从这里开始没有一个字符符合 d 字段的形状
------------------------------------------------------------------------------
结论   : 没有匹配
  停在第 0 段、第 0 个字符：{:d} 从这里开始没有一个字符符合 d 字段的形状
```

匹配成功时 `--explain` 会列出所有候选切分点，标出哪些能「逐字节写回」，
哪些只是「去掉填充后一致」，最后打印实际采用的切分：

```bash
$ python unformat.py "{c:02d}" "100" --explain
格式串 : {c:02d}
输入   : '100'

逐段候选判定（能逐字节写回的切分点会优先采用）
------------------------------------------------------------------------------
  [ 0] 字段 {c:02d}        @  0:1   取 '1'
       去掉填充 '1' -> 值 1 -> 写回 '01'  通过（仅去填充后一致）
  [ 0] 字段 {c:02d}        @  0:2   取 '10'
       去掉填充 '10' -> 值 10 -> 写回 '10'  通过（可原样写回）
  [ 0] 字段 {c:02d}        @  0:3   取 '100'
       去掉填充 '100' -> 值 100 -> 写回 '100'  通过（可原样写回）
------------------------------------------------------------------------------
结论   : 匹配成功
  采用切分 : {'c': (0, 3)}
  按名字 : {'c': 100}
```

「优先采用能逐字节写回的切分点」这条排序规则很关键。`"001002"` 配
`{x:03x}{y:03x}` 时，如果按最短优先，第一个字段会先吃掉 `"0"`，
剩下的 `"01002"` 就被硬读成一个数（256）；按写回复原度排序后，
`"001"` 因为 `format(1, "03x") == "001"` 排到最前，两个字段正确切成 1 和 2。

## 支持的格式描述

字段写法：`{name:spec}`，`name` 可省略（按位置收集），加 `?` 表示可选字段。

| 类别 | spec 例子 | 读出来的值 |
|------|-----------|------------|
| 字符串 | `{}`、`{:s}`、`{:>12s}`、`{:^12s}`、`{:*^12}`、`{:10.3}` | `str` |
| 词 | `{:w}` | `str`，只收字母/数字/下划线 |
| 十进制整数 | `{:d}`、`{:05d}`、`{:5d}`、`{:n}`、`{:,d}`、`{:_d}` | `int` |
| 其他进制 | `{:b}`、`{:o}`、`{:x}`、`{:X}`、`{:#x}`、`{:06x}` | `int` |
| 浮点 | `{:f}`、`{:.2f}`、`{:08.2f}`、`{:e}`、`{:g}` | `float` |
| 百分数 | `{:.1%}`、`{:,.1%}` | `float`（`12.3%` → `0.123`） |
| 日期时间 | `{%Y-%m-%d}`、`{%Y%m%d}`、`{%H:%M}`、`{%Y-%m-%d %H:%M}` | `date` / `time` / `datetime` |

支持 `[[fill]align][sign][#][0][width][grouping][.precision][type]` 这一整套
描述，因为复原判定直接调用 `format()`，语义由 Python 自己保证。
`{{` 和 `}}` 是字面量花括号。

几个行为约定：

- **填充字符不属于值**。`"{name:.>16.16}"` 读 `".............Joe"` 得到 `"Joe"`。
- **宽度是下限**。`"{c:02d}"` 读 `"100"` 得到 `100`，不会截成 `10`。
- **精度是有损的**。`"{:.2f}".format(3.14159)` 写出的 `"3.14"` 读回来是
  `3.14`，不是 `3.14159`；这是 `format()` 本身丢掉的信息，不是解析错误。
- **不合法日期返回 `None`**，不抛异常。`"2024-02-30"` 结构像日期但日历上不存在。
- **空字符串字段可读**。`"Hello {}!"` 读 `"Hello !"` 得到 `""`。
- **可选字段**：`"{honorific?} {given} {sur}"` 既能读 `"Mr Richard Jones"`，
  也能读 `"Jens Engels"`（缺失时为空串，并跳过紧跟的分隔空白）。

未知类型、精度没写数字、花括号不配对等属于格式串写错，会抛 `FormatError`
并在命令行里返回退出码 2。

### 刻意不做的事

- 不支持自定义类型转换表、自定义类型注册、命令行求值等扩展机制——
  那些东西会让「写出去 / 读回来」不再共用同一段描述。
- 不做嵌套字段、属性访问、索引访问的求值。
- 面向的是**日志行、文件名、协议文本**这类短字符串，不是大文件流式解析。

## 实测数据

在本机 Python 3.13 上测得（可直接复跑 `python -m unittest discover -s tests`）：

| 指标 | 结果 |
|------|------|
| 回归测试 | 48 项全部通过 |
| `format → parse → format` 逐字节复原（28 组 spec × 值） | 28 / 28 |
| 编译一次 + 解析 10000 行日志 | 0.330 s，约 33.0 µs/行 |
| 源码规模 | 单文件 918 行，测试 343 行 |

计时方式：同一个解释器里各跑 5 轮、取最快一轮，格式串 `id={id:d} level={level}`。

**速度不是这个工具的强项。** 每个字段都要枚举可能的切分点并调用
`format()` 复核，比「一次正则匹配」的实现慢约 6 倍（同一批 10000 行，
纯正则路线 0.055 s、约 5.5 µs/行）。换来的是同一段 spec 写出与读回的一致性，以及
失败时能说清楚原因。如果场景是每秒处理几十万行、格式串固定且简单，
正则或 `str.split` 更合适；如果是每天读几百行日志、格式串经常改，
这里省下的是反复调正则的时间。
